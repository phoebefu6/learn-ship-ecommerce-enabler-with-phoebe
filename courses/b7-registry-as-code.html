The metric registry as code

Take one real quarter of Olist orders and ask for its GMV. You get R$ 2,858,289.74, or R$ 3,332,156.97, or R$ 2,807,156.64, and every one of them is right. The problem is never the arithmetic; it is that a dashboard, a board pack and a brand statement each quietly picked a different one and called it the same word. Tonight you write the registry that stops that: one YAML entry per metric name, one Python reader that everything imports, and three tests that fail the moment somebody changes a definition without saying so.

Part 1 · covers GMV variants on one real quarter

Three GMVs from one real quarter

6 min live

Q2 2018 on Olist, April to June, order lines by purchase date: 19,947 orders. Filter the same rows three ways and you get three totals, each with a sound argument behind it. The registry does not choose the "true" one. It gives each one its own name, so that nobody can ever again say "GMV" and mean two of them.

DefinitionQ2 2018 on OlistThe argument for it
Placed, any status, items onlyR$ 2,858,289.74The demand the stores generated; what the trading team steers
Placed, any status, items + shippingR$ 3,332,156.97What the buyer was charged; matches a marketplace headline that counts shipping
Delivered only, items onlyR$ 2,807,156.64Closest to the money that settles; what a GMV-linked fee should rest on
Delivered only, items + shippingR$ 3,273,631.74Settled-ish, buyer-side view

Cancelled or unavailable orders in the quarter add up to only R$ 8,559.48 across 50 orders, so on this file the status filter moves the total far less than the shipping choice does. On an enabler's own estate, with returns and failed deliveries, the order flips. Either way, the size of the gap is not the point; the point is that a board pack and a brand statement built on two of these rows will disagree, and nobody will know why until somebody opens both queries.

Self-studyThe same spread, on Serai's constructed quarter3 min▶

The leader track uses one constructed Serai quarter to make the same point with fees on top. GMV placed including shipping $48.6M, placed excluding shipping $45.0M, settled net of cancellations and returns $39.2M. Divide the same $1,764,000 of retainers and GMV share by each and the take rate reads 3.63, 3.92 or 4.50 percent; drop the retainers and it is 2.00 percent. Every figure there is constructed, and your numbers will differ. The Olist quarter above is the real-rows version: the same spread, measured.

The definitions themselves (GMV, take rate, what counts as an order) are taught properly in the GMV equation session of the ecommerce metrics track. The enabler twist is that an enabler reports someone else's GMV, often on three marketplaces with three conventions, and bills against it.

Real world

A listed marketplace's GMV counts shipping and unsettled orders. Sea Limited's annual report for fiscal 2019 defines Shopee's GMV as the value of orders on the marketplace and says the calculation "includes shipping and other charges", and it counts each confirmed order regardless of whether the transaction is settled or the item returned. That is a clear, written choice, and it is the middle row of the table. An enabler whose own GMV is delivered-only will always look smaller than the marketplace's figure for the same stores, and that is fine, as long as both definitions are written down.

Part 2 · covers the registry entry as code

A registry entry is code

6 min live

A metric definition in a wiki page is a hope. The same definition as a YAML entry, read by the code that computes the number, is a contract: change the entry and every number built on it changes with it, in one commit, with a name and a date. Ten fields are enough, and each one has a reader.

LiveThe ten fields, and the three that answer the reader4 min▶
FieldWhat goes in itWho reads it
description + sql"A clear definition of the metric and how it is calculated"Board pack, every analyst
why_useful"The reasons why the metric provides useful information"Board pack, brand statements
how_used"How management uses the metric in managing or monitoring the performance of the business"Board pack, the owner
grainThe row the SQL sums over, and the date it keys onDashboard, anyone joining it
sourcesTable and column for every input: the lineageData engineering, when a source changes
ownerOne team, not a person's nameWhoever gets paged when a test fails
version, valid_from, change_logThe history: what changed, when, and whether prior periods were restatedThe CI test, auditors, next year's you

The quoted wording in the first three rows is the SEC's, below. Put the three questions in the schema as required fields and the reader loads nothing that cannot answer them.

Self-studyOne reader, and the spec sheet it replaces3 min▶

The YAML is half of it. The other half is that exactly one module reads it. If the dashboard parses metrics.yaml with its own code and the board pack script with another, you have two readers and, the first time somebody adds a field, two behaviours. registry.py below is thirty lines, and every consumer imports it: load() refuses an entry with a missing field, compute() runs the entry's own SQL. Nobody writes SUM(price) anywhere else.

How to write a good definition in the first place (the one-page spec, the edge cases, the sign-off) is taught in the metric spec sheet session of the ecommerce metrics track, and governance around it in its metric governance session. The registry is the spec sheet made executable: same content, but now a machine checks it on every change.

Real world

A public checklist for a key metric. The US SEC's 2020 guidance on key performance indicators in MD&A says the Commission would generally expect, alongside such a metric, a clear definition and how it is calculated, the reasons it provides useful information, and how management uses it. If the calculation changes, it says to consider disclosing the differences, the reasons and the effects on amounts previously reported. Read it here as what it is: a public example of the three questions any serious reader asks of GMV or active sellers, and a good schema for three required fields. What any exchange requires of a listing is a question for counsel, not for a YAML file.

Part 3 · covers tests on metric definitions

Tests that fail when a definition drifts

4 min live

Definitions drift for good reasons. Somebody decides cancelled orders should not count, adds one line to the SQL, and the quarter's GMV moves by R$ 8,559.48 without a meeting. The registry cannot stop the decision, and should not. It can refuse to let it happen silently. Three tests do it.

LiveThree tests, three different failures3 min▶

Golden numbers. Freeze one past period and write down the approved value of each metric: gmv_placed for Q2 2018 is R$ 2,858,289.74, active_sellers_1000 is 552. The data for a closed quarter does not change, so if the computed value moves, the definition did. This is the test that catches the one-line SQL edit.

Reconciliation. Two independent routes to roughly the same money should agree within a tolerance you write down in advance. Items plus shipping for the quarter is R$ 3,332,156.97; the payments table for the same orders is R$ 3,332,386.55; the gap is R$ 229.58. The tolerance in the build-along is 0.01 percent of payments, R$ 333.24. When a join starts fanning out or a table is loaded twice, this test fails first.

Definition change. Store a fingerprint of each approved SQL next to its version. If the SQL changes and the version does not, or the change log has no entry that says prior periods were restated, fail. This is the test that turns "somebody tidied the query" into a reviewed decision.

Self-studyWhat a restatement is, in practice2 min▶

When gmv_placed moves to v2, three things happen in the same commit: the version goes up, the change log says what changed and why, and every prior period that anyone will compare against is recomputed on v2 and the golden value updated. Last year's board pack is not edited; next year's shows both, with a line saying which definition each column uses. A trend that crosses a definition change without restating is the most common way a chart lies with every number on it correct.

Real world

Constructed, and common: two take rates in one meeting. On Serai's constructed quarter, the finance deck divides fees by GMV placed excluding shipping and shows 3.92 percent; the brand team's deck divides by settled GMV and shows 4.50 percent. Both queries are correct and both are called "take rate". With a registry, the two numbers have two names, take_rate_placed and take_rate_settled, and the board sees one of them with its definition printed under it. Every figure in this story is constructed; your numbers will differ.

Write the registry: three GMVs, two active-seller counts. Each entry answers the three reader questions (description, why_useful, how_used), carries its SQL, its grain, its lineage and its history. The dates are half-open, >= start and < end, so a quarter never double-counts its last second.

Write the one reader. load() refuses any entry missing a required field, so an entry that cannot answer the three questions never reaches a dashboard. compute() runs the entry's own SQL with named parameters; SQLite is in the standard library, so the SQL in the YAML is exactly what runs.

★ Step 3 · registry.py# registry.py - the ONE reader; dashboards, board pack and tests import it import sqlite3, yaml, pandas as pd from pathlib import Path DATA = Path.home() / ".cache/kagglehub/datasets/olistbr/brazilian-ecommerce/versions/2" REQUIRED = ["description", "why_useful", "how_used", "grain", "sql", "sources", "owner", "version", "valid_from", "change_log"] def load(path="metrics.yaml"): reg = yaml.safe_load(Path(path).read_text()) for name, m in reg.items(): missing = [f for f in REQUIRED if f not in m] assert not missing, f"{name} is missing {missing}" return reg def connect(): db = sqlite3.connect(":memory:") for t, f in {"orders": "olist_orders_dataset.csv", "items": "olist_order_items_dataset.csv", "payments": "olist_order_payments_dataset.csv"}.items(): pd.read_csv(DATA / f).to_sql(t, db, index=False) return db def compute(reg, db, name, start, end): (value,) = db.execute(reg[name]["sql"], {"start": start, "end": end}).fetchone() return round(value, 2)

Compute every metric for Q2 2018. Five names, five numbers, and each one matches the table in Part 1. Note what the two seller counts say: 1,680 sellers traded at all, but only 552 sold R$ 1,000 of delivered goods. The file has 3,095 sellers, and 1,653 had a delivered order in the quarter. Four honest answers to "how many active sellers".

★ Step 4 · run.pyfrom registry import load, connect, compute reg, db = load(), connect() Q2 = ("2018-04-01", "2018-07-01") for name in reg: print(f"{name:<26} v{reg[name]['version']} {compute(reg, db, name, *Q2):>14,}") # prints: gmv_placed v1 2,858,289.74 gmv_placed_with_shipping v1 3,332,156.97 gmv_delivered v1 2,807,156.64 active_sellers_any v1 1,680 active_sellers_1000 v1 552

Lock the approved definitions. A short hash of each entry's SQL (whitespace normalised, so re-indenting is not a change) and its version, written to a file you commit next to the YAML. Re-run this only when a definition change has been reviewed.

★ Step 5 · lock.py# lock.py - run once when a definition is approved; commit metrics.lock.json with the YAML import json, hashlib from registry import load fp = lambda sql: hashlib.sha256(" ".join(sql.split()).encode()).hexdigest()[:12] lock = {n: {"version": m["version"], "sql": fp(m["sql"])} for n, m in load().items()} json.dump(lock, open("metrics.lock.json", "w"), indent=1) print(lock["gmv_placed"]) # prints: {'version': 1, 'sql': '9c82b797f930'}

Write the three tests, with plain asserts, and watch them pass. Golden values for the frozen quarter, the payments reconciliation with its tolerance stated in the code, and the definition-change check against the lock file. In CI this is the file that runs on every pull request touching metrics.yaml.

★ Step 6 · test_registry.pyimport json, hashlib from registry import load, connect, compute reg, db = load(), connect() Q2 = ("2018-04-01", "2018-07-01") fp = lambda sql: hashlib.sha256(" ".join(sql.split()).encode()).hexdigest()[:12] # 1 golden numbers: the approved value of each metric for one frozen quarter GOLDEN = {"gmv_placed": 2858289.74, "gmv_placed_with_shipping": 3332156.97, "gmv_delivered": 2807156.64, "active_sellers_any": 1680, "active_sellers_1000": 552} fails = [] for name, want in GOLDEN.items(): got = compute(reg, db, name, *Q2) ok = got == want print(f"golden {name:<26} {got:>14,} {'PASS' if ok else 'FAIL, want ' + format(want, ',')}") if not ok: fails.append(name) # 2 reconciliation: items + shipping against the payments table, same orders (paid,) = db.execute("""SELECT ROUND(SUM(p.payment_value), 2) FROM payments p WHERE p.order_id IN (SELECT o.order_id FROM orders o JOIN items i USING (order_id) WHERE o.order_purchase_timestamp >= ? AND o.order_purchase_timestamp < ?)""", Q2).fetchone() gap = round(paid - compute(reg, db, "gmv_placed_with_shipping", *Q2), 2) TOL = 0.0001 * paid # stated tolerance: 0.01 percent of payments print(f"recon payments {paid:,} gap {gap:,} tolerance {TOL:,.2f} {'PASS' if abs(gap) <= TOL else 'FAIL'}") if abs(gap) > TOL: fails.append("reconciliation") # 3 definition change: new SQL needs a version bump and a change_log entry that says restated lock = json.load(open("metrics.lock.json")) for name, m in reg.items(): changed = fp(m["sql"]) != lock[name]["sql"] bumped = m["version"] > lock[name]["version"] logged = any(e["version"] == m["version"] and "restated" in e["change"] for e in m["change_log"]) if changed and not (bumped and logged): print(f"version {name:<26} SQL changed, still v{m['version']}, no restatement: FAIL") fails.append(name + " version") print("ALL PASS" if not fails else f"{len(fails)} FAILED: {fails}") assert not fails # prints: golden gmv_placed 2,858,289.74 PASS golden gmv_placed_with_shipping 3,332,156.97 PASS golden gmv_delivered 2,807,156.64 PASS golden active_sellers_any 1,680 PASS golden active_sellers_1000 552 PASS recon payments 3,332,386.55 gap 229.58 tolerance 333.24 PASS ALL PASS

Now drift one definition, on purpose. Somebody decides cancelled orders should not count in gmv_placed, adds one reasonable line to its SQL, and does not touch the version. Run the tests again. The golden test catches the number moving by exactly the R$ 8,559.48 of cancelled and unavailable orders, and the version test names the missing bump. The script ends in an AssertionError, exit code 1, and CI stops the merge.

Extend the session 1 registry, do not start a second one. The estate registry already knows every table's grain and owner; the metric registry's sources should point at those same table names, so a grain fix in one place reaches every metric built on it. Check yourself

Three questions

Clear all three and Analyst session 7 gets stamped in your passport.

1 · On Olist Q2 2018, one query returns R$ 2,858,289.74 and another returns R$ 3,332,156.97, both labelled GMV. What should the registry do?

Both are defensible; the first is item value, the second is what the buyer was charged, which is the marketplace-headline convention. The failure is one word covering two numbers. Two names end it.

2 · Which three fields map onto the three questions the SEC's 2020 guidance lists for a key metric?

The guidance expects a clear definition and calculation, the reasons the metric is useful, and how management uses it. The other fields matter too, for lineage and history, but those three are the reader's questions, and making them required means no entry loads without them.

3 · After a one-line SQL edit, the golden test reports gmv_placed as 2,849,730.26, want 2,858,289.74. What is the right response?

The data for a closed quarter cannot move, so the definition did, by exactly the R$ 8,559.48 of cancelled and unavailable orders. The test is working. The fix is to make the change a visible decision, not to make the test quiet.
